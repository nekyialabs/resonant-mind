# v3.2 → v4 migration acceptance evidence

> **This is the record made for 4.1.0 (21 October 2026), and the body below is kept as it was then.** Where it says "release candidate" or "has not shipped", read it as of that date: the migrator shipped in 4.1.0. Later evidence is in the [changelog](../CHANGELOG.md): 4.1.1 (the first real D1 migration, by a v3.2 user), 4.1.3 (empty dates and times become decisions), and 4.1.4 (a real `wrangler d1 export` as a test fixture, and `normalise-source` for drifted D1/SQLite sources). This record does not cover `normalise-source`. Its restore SQL has not yet been run against a real migration.

This is a local operator-assisted acceptance record for the release-candidate implementation. It is **not** a support or release declaration. The CLI reads only the exact public v3.2 PostgreSQL schema and the exact post-0003 D1/SQLite schema, exports read-only snapshots, writes only to a distinct fresh v4 target, and never self-attests cutover.

## Scope and safety boundary

- Source is read-only: PostgreSQL uses `REPEATABLE READ READ ONLY`; SQLite opens with `readOnly: true` and source before/after hashes are compared.
- The checked-in SQL fixtures are byte-identical to tag `v3.2.0`; fixture verification is required before migration tests.
- Bundles are encrypted by default. Plaintext requires both explicit acknowledgement flags. The compiled policy and the relational staging plan, which hold the migrated content too, follow the same rule with the same passphrase file (`--allow-plaintext-artifact --acknowledge-plaintext-risk` for plaintext), and no command replaces an existing output.
- The target must be a distinct, empty PostgreSQL database. Released `migrations/postgres/*.sql` are not modified.
- Remote D1 export, R2/provider execution, re-embedding execution, deployment, cutover, and rollback are operator-controlled or external phases. The CLI does not invoke Wrangler, Cloudflare, embedding providers, deployment, or destructive rollback.
- An interrupted pre-commit run is not a general crash-resume promise. Start again against a fresh target; checkpoint files are integrity diagnostics only and semantic skips/truncation refuse.

## Live PostgreSQL evidence (2026-10-20, local)

Until this work the PostgreSQL path had never executed against a real database: the table above records the live E2E as skipped. It was run on 2026-10-20 on a throwaway local cluster, PostgreSQL 18.6 with pgvector 0.8.1, on branch `fable/migrator-finish`, through the PostgreSQL integration suites (`TEST_ADMIN_DATABASE_URL` set; each test creates and drops its own scratch databases). Running it found and fixed real defects, which is why it is recorded here. It was run twice: first through the library functions, then (after the CLI gained the missing steps) through the CLI alone.

Result of the migrator PostgreSQL suites on that cluster, final run (after the sixth round below, on 2026-10-21): **11 files, 45 tests, all passed** (`postgres-source.integration` 4, `postgres-source-session.integration` 2, `target-fresh.integration` 11, `postgres-spec.integration` 14, `cli-postgres.integration` 2, `cli-flow.integration` 3, `e2e-postgres.integration` 1, `e2e-postgres-rich.integration` 1, `e2e-sqlite.integration` 1, `v4-checks.integration` 3, and the v4 application suite `postgres-v4.integration` 3). The non-live suite, `npx vitest run`, passes with the live tests skipped (61 files, 654 tests passed, 42 skipped, after the sixth round); `npm run verify` is green. The new non-live image suite (`image-fingerprints`, 30 tests), the database-free SQLite CLI flow and the round-four suite were also run on the cluster's host (Linux), which also exercises the unreadable-file refusal that a Windows run skips (14 files, 109 tests, all passed).

What those runs prove, on PostgreSQL 18.6 only:

- **The fingerprint describes a real v3.2 database.** `scripts/v32-to-v4/spec/v3.2-postgres.json` is generated, not hand-written: `generate-postgres-spec.mjs` applies the byte-verified `postgres.sql` fixture to a scratch database, reads the catalog through the same adapter code the CLI uses, and writes the fingerprint. A test requires the committed file to equal that output, and a database-free test now compares it with a catalog derived from the SQL alone, in every field (including index method, operator class and options, and defaults exactly, not by prefix). A schema with an extra column, a changed default or type, an added check, a SET NULL or RESTRICT foreign key, a renamed index or primary key, a dropped unique constraint, a different vector dimension, or an extra table is refused (tested live). There is no version-dependent rewriting of catalog text.
- **The whole operator flow, through the CLI alone, as separate processes.** `cli-flow.integration` runs `inspect-source`, `export`, `verify-bundle`, `draft-decisions`, `apply-decisions`, `compile-policy`, `plan-relational`, `inspect-target`, `prepare-target`, `dry-run`, `import`, `validate` and `status` on (a) the rich PostgreSQL fixture, (b) a SQLite source and (c) a D1 SQL export, each to a fresh v4 target. Each carries one image row. Before any external evidence the state is `data-imported-images-pending`; the picture is then copied with `copy-images` (a missing source object refuses the copy and leaves no receipt), `validate --image-target-dir --image-source-dir` re-hashes the copy and its source (`data-imported-not-search-ready`, `images.basis: tool-rehashed-source-and-target`; before the sixth round, `tool-rehashed-objects`), and once re-embedding receipts for the CLI-planned jobs (the image job's receipt names the copied object) are supplied, all three end at `ready-for-cutover`. The rich run also finds an object changed in the target after the copy, a re-embedding receipt for another object, and reaches `ready-for-cutover` a second time on a signed receipt (`signed-receipt-attested`), refusing a signed receipt that fingerprints nothing. The connection strings and the password appear in no output and no artifact of any run. A non-live SQLite run covers the source-side steps and their refusals (an unreviewed draft will not compile; an incomplete, wildcard, disallowed or stale review is refused by `apply-decisions`; an edited compiled policy is refused by `plan-relational`).
- **Validation reads the live systems and finds damage.** `validate` re-reads the source and the target itself. On a clean run it compared several hundred cells from the source and from the plan with the target, found nothing, and reported by kind what differed from the source and why (a remapped id, an enum alias, a normalized timestamp, a reviewed decision, a v4 default for a NULL). Against clones of the migrated target it found: a changed text, a timestamp rounded to the millisecond, a missing row, an extra row, a changed enum value, an id sequence left behind the data, a CHECK constraint that the released schema does not have (found, and not run), and the importer's own receipt row removed; each by a check that names it. It also found a source row changed after the export, an edited plan, an edited receipt, a different reviewed decision file, and a target that is the source. A database-free test (`compare-live`) shows the comparison catches a transform that rounds to milliseconds even when the target faithfully holds the transform's output.
- **Session independence, and a stand-in for a pooler.** The source's `TimeZone`, `DateStyle`, `search_path` and `extra_float_digits` are set with `set_config(..., true)` inside the read-only snapshot transaction, not as startup options. With the database defaults changed to a search_path without `public`, another time zone, a non-ISO date style and `extra_float_digits = -3`, the catalog and every row's text are identical (and an unprotected client sees the difference). A proxy that answers a startup `options` parameter with "unsupported startup parameter: options", as PgBouncer does, refuses the old style of connection and passes the new one, with identical results.
- **The fresh-target check, live.** A fresh target (with or without `vector`, in `public` or its own schema) is accepted; a user table, a view, a sequence, a function, a type, a table in another schema, an empty non-public schema and a non-vector extension are each refused. Another session's temporary tables no longer make an empty database look used (found by this test), while a real table next to them is still refused.
- **Value fidelity with every v3.2 table populated.** `e2e-postgres-rich` reads the source and the target with the same SQL and requires equality for every migrated column: text byte for byte (including a 13 KB observation with quotes, newlines and unicode), integers, ids, self references, JSON-in-text, and all timestamps to the microsecond in UTC, plus routing to people/nodes, observation-version numbering, the reviewed tension choice, the dormant-to-orphan translation, the loss audit, and no legacy vector in v4. `validate` now does the equivalent for any migration, as a product feature.

Defects found and fixed by running it. First round: the fingerprint above; `jsonb` (`embeddings.metadata`) was parsed into an object that the bundle rejects, so any real source with an embeddings row failed to export; `prepareTarget` threw whenever a plan was supplied; the transform rounded timestamps to milliseconds; and `SET NULL` foreign keys were read as `NO ACTION`. Second round: no command produced the decision draft or the relational plan, and `validate` consumed snapshot files nothing could write; `import` printed its receipt but never saved it; the target phases could not connect to a PostgreSQL without TLS, and could not be given a SQLite or D1 source at all; a refusal from an asynchronous command ignored `--json`; an empty target was refused when another session held a temporary table; `observations.archived_at` and `last_accessed_at` skipped timestamp normalization; a naive space-separated timestamp lost its microseconds under a reviewed timezone; observation versions were numbered by comparing timestamp text and text ids (so `...05.123456Z` sorted before `...05.123Z`, and `10` before `9`); `extra_float_digits` was not pinned; a reviewed merge left a false "v4 filled in a NULL" entry.

Third round (an independent review of the second round, fixed with a test that failed first, except where a new module made "failing first" mean "the module did not exist"). A reviewed choice could be applied to a sibling field: two broken references on one row shared one decision id, so the second was silently dropped from the draft and a choice matched by row hash and kind; a decision id now includes the column and a choice binds to exactly one item, and an ambiguity is a refusal. Image evidence was judged against the image plan the operator supplied: with the old code an empty image plan and a matching receipt gave `images_complete: true` for a migration that planned two images (reproduced against the old function); `validate` now requires the supplied plan to equal, in canonical form, the inventory it derives itself, every imported image row to be listed in it, and `plan-images --plan` hands that inventory out. Re-embedding receipts were not checked against the content the target holds. Invalid cutover evidence fell back to `ready-for-cutover`. `status` accepted an edited report with a recomputed plain hash (it now needs a keyed seal). JSON was compared after `JSON.parse`, so `12345678901234567891` equalled `12345678901234567000`. The compiled policy and the plan held the migrated content in plaintext. `compile-policy`, `plan-images`, `plan-reembed`, `copy-images` and `dry-run` replaced an existing output. `new Date` read `2026-02-30` and `T24:00` as other days. The validator ran CHECK expressions read from the target's catalog (reproduced live: a target CHECK that raises an exception raised it inside the validator). A decision file for another migration was accepted. A refusal could name a report path that the redactor had rewritten into one that does not exist.

Fourth round (a focused review of the third round's external phases; each fix has a test that failed before it, and the new tests are in `external-evidence`, `round-four`, `v4-checks.integration` and `cli-flow.integration`). The principle for work the tool cannot observe (image copies, re-embedding, cutover): require explicit evidence that the operator's invocation decides on, never a field inside the evidence, and name each state for what it rests on. (1) Whether an image receipt needed a signature was read from the receipt's own `external_handoff`, so an unsigned receipt that did not claim to be a handoff completed the images; a signature is now required unless the operator names the copy directory (`--image-target-dir`) and the tool re-hashes every object itself, or always when a trusted key is configured, and `validateImageReceipt` requires one by default. (2) Re-embedding receipts agreed only with themselves; they are now held to a model the operator states (`--embedding-model`) and to the dimension of the target's `embeddings.embedding` column, and are named `receipts-attested`, `observed_by_tool: false`. (3) `status` showed a historical seal as if current; it now says it reports what `validate` proved at `validated_at` for that target and that only `validate` checks the target now. (4) JSON with a repeated key at any depth passed the number check and compared equal to its last value; it is now a `malformed-json` decision item and a comparison failure, exponents are compared as exact integers, and `-0` equals `0` by decision (PostgreSQL numeric has no negative zero). (5) The plan was compared with the target only in the columns a plan row states; every column the target holds is now compared (NULL, the column's own default, a computed value, or the value v4's trigger derives for `identity.kind`; anything else is `target-column-not-in-plan`), in the re-embedding projection too, and for an image job the stored row is held to the planned row instead of only checking that it exists. Running it live found that `identity.kind` is filled by a trigger and was unplanned, which is why the derivation is re-computed. (6) The cutover state is `complete-operator-attested`. (7) A partial or expression unique index is a finding, an INCLUDE column no longer counts as a key column, and a sealed artifact's header and authentication carry the migration id.

Fifth round (found by running a v3.2 source with an image through the CLI to the ready state; each fix has a test, mostly in `image-fingerprints`, plus the live flows in `cli-flow.integration` and the three end-to-end suites). (1) v3.2 stores no hash, size or MIME type for an image, so the plan's `expected_*` fields were `null` and neither `copy-images` nor the receipt check could succeed: such a migration stayed at `data-imported-images-pending` for good. `copy-images` now fingerprints each source object itself (SHA-256, size, MIME type from the content's magic bytes), refuses the whole copy, with no receipt, for a source object that is missing, unreadable, a symlink or behind one, outside the source root, not an image, or changed between the fingerprint and the copy, and reads the copy back and hashes it; `validate --image-target-dir` holds the re-read objects to the plan's value where the plan has one and otherwise to the fingerprint in the receipt; a signed operator receipt for objects the tool cannot read has to carry the SHA-256, size and MIME type observed for every object. (2) The same defect was in the re-embedding check: an image job states no object for a v3.2 source, so its receipt could never be accepted (`object-binding-mismatch` for every receipt). A receipt for an image job must now name the object, and it is held to the object that was copied. (3) The states are named `tool-rehashed-objects` and `signed-receipt-attested`, with `images_fingerprint` saying whether the plan or only the receipt's fingerprint pinned the objects. (4) `status` exited 0 for an `unverified` report; it exits 3 (refused stays 2). Exit 0 is a verified report, not a ready one.

Sixth round (a human review of the pull request; each fix has a test, and the tests that exercise behavior failed before the fix: `review-decisions`, `defaults-evaluated`, the offline-comparison cap in `external-resilience`, the unstated-column case in `external-evidence` and `round-four`, and the new `image-fingerprints` describe). (1) The decision draft holds only a hash of each observed value, so the owner could not decide a merge, a timezone or a repaired JSON value from it, and an agent that paraphrased the bundle framed the options. `review-decisions` now shows the owner the real values, locally, with each item's allowed choices and what they do; its terminal output and its self-contained HTML file hold memory content and nothing else does (`review-decisions.test` drives it as a separate process on a SQLite source whose content carries markers and hostile text, requires the markers in the review and in no other output or artifact, and tokenizes the HTML to fail on any tag, attribute, URL or script outside a small allowed set). Every chosen item now records who stated it (`owner` or `owner-accepted-agent-suggestion`) and, optionally, the owner's bulk rule verbatim; the statements are in the reviewed file, the compiled policy and the validation report. The runbook and the guide say that the owner reads the values in `review-decisions` rather than an agent's summary and that a delegation ("you decide", "approve all") is not a choice. (2) With `--image-target-dir` and no trusted key, a v3.2 plan states no values, so the copied objects were held only to the fingerprints of a plain receipt that could be written from the target directory; `validate --image-source-dir` now re-hashes the source objects as well, the filesystem copy seals its receipt with the migration passphrase, and an unsigned receipt completes images only with the seal and with the tool having seen both ends (otherwise the images stay pending, with the reason in the report); the bases are renamed for what they rest on. (3) `reconcileMigration`, an offline comparison of caller-supplied snapshots that took a caller-asserted `toolObservedImageObjects`, is capped below ready, and the ready-state assertions in the end-to-end tests go through `validateCommand` with live reads (`e2e-postgres`) or through the CLI (`cli-flow.integration`); the SQLite end-to-end test, which has no live target, asserts only that the offline comparison cannot read as ready. (4) A column the plan does not state and whose default is `now()`, `CURRENT_TIMESTAMP` or `transaction_timestamp()` must hold exactly the import's time, and a `nextval(...)` column an integer within the sequence's range; any other default is a finding that names the column, so the state cannot be ready. `v4-checks.integration` checks that no default in the released schema is one the validator cannot evaluate.

Known behavior that is by design and now recorded in the product, not only in a test comment: a source `entities.created_at`, `updated_at`, `salience` or `primary_context` of NULL becomes the import time, `'active'` or `'default'` in v4, because v4's own routing trigger writes `COALESCE(...)`. Each case is a `null-replaced-by-v4-default` entry in the loss and audit report, and `validate` checks that the target holds exactly that default (for a timestamp, the import transaction's own time, read from the importer's receipt record) and that every recorded case is visible. `entities.intentionally_isolated` and `observations.charge_note` have no v4 column and are dropped with a loss-audit entry (the `charge_note` reason now says what is true: v3.2 creates the column, v4 has none). A PostgreSQL `timestamptz` is now exported as RFC 3339 text, so the row hash of every row with one changed: a decision draft or reviewed manifest made before this branch is refused as stale; export again and draft again. The migrator has not shipped, so this affects only development drafts.

What is still **not** proven:

- **PostgreSQL 17.** Proven on 16 (CI) and 18 (locally); real v3.2 users run 16 or 17. Nothing in the catalog or validation queries is known to differ on 17 (the `pg_constraint` filters exclude the not-null constraints PostgreSQL 18 adds), but 17 has not been run.
- **A real pooler.** The pooler support rests on a proxy that rejects startup options and on a session with changed defaults, not on Neon or PgBouncer. A transaction is one server connection under transaction pooling, so the single read-only transaction should hold, but it has not been run through one. Supabase-style layouts with `vector` outside `public`, large tables, concurrent writes to the source during the snapshot, and restore rehearsal are also unproven.
- **Scale.** `validate` holds the bundle's rows, the source's and the target's in memory at once (as `loadVerifiedBundle` already holds the bundle). It has not been measured on a large database.
- **Images/R2 and re-embedding execution.** The image copy of a v3.2 source is exercised live (round five, below). What remains is below the tool's reach: an R2 or other external store, and a real provider run. The no-evidence states (`data-imported-images-pending`, `data-imported-not-search-ready`) and the re-embedding evidence path are exercised live (with receipts the test writes itself, standing in for a provider); copying real image files, a signed external R2 receipt and a real provider run were not exercised through the CLI. `plan-images --plan` now takes the inventory from the relational plan, and an image plan that is not that inventory is refused live (an empty plan with a matching receipt is exercised in `cli-flow.integration`), but a full image run with a filled, matching receipt exists only as a database-free unit test (`external-evidence.test`). A plan with no images, or no jobs, needs no external evidence. The re-embedding content check compares the target's rows with the plan column by column (by the v4 column type) and also every column the plan row does not state; for an image job the stored `images` row is held to the planned `images` row the same way, and the object's bytes are proven only by the image evidence (the tool's re-hash of `--image-target-dir`, or a signed receipt, which is attested). Round four left a gap here: the fixture's one image row has no `sha256`, `size` or `mime` (v3.2 `images` has no such columns), so its inventory entry could not be copied or receipted at all and a real v3.2 source with images could not reach `images_complete`. Round five closes it (below). What the image evidence still does not prove: that the original source objects still hold the bytes that were copied (`validate` does not read the source image directory, so for a v3.2 source the receipt's fingerprint is the only record of the originals), and that an operator-signed receipt for R2 objects is true (a signature says who said it). No R2 store, and no signed receipt made from a real bucket, was involved.
- **What `validate` still takes from the compiled policy.** It derives the expected value of every cell from the source rows and the reviewed decisions: instants, JSON (digit for digit), enum and context mappings (accepted only when the policy recorded that exact value), version numbers, the values a reviewed merge gives the survivor, a reviewed rename, the reason a row is skipped as merged, and the link a reviewed decision gives a reference. It still takes, unverified a second time, the id map (target ids and tables), the name map used for relation endpoints, and the list of excluded rows with the rows excluded because they depend on an excluded row. They come from the same reviewed decisions `validate` recompiles itself, so a wrong one needs a wrong compile, not a wrong file; but a bug in the compiler's exclusion or id logic would be seen by neither side.
- **The report seal.** `status` verifies a keyed seal made from the migration passphrase file. It stops an edited report and a report from elsewhere; it does not stop the holder of the passphrase file from sealing a report. A report validated without a passphrase file carries no seal and `status` calls it unverified, not proof.
- **CHECK expressions on other PostgreSQL versions.** `spec/v4-checks.json` was generated on PostgreSQL 18.6 and is compared with what PostgreSQL prints for the released constraints. On PostgreSQL 16 the `v4-checks.integration` test passed in CI, so 16 prints them the same. PostgreSQL 17 might print an expression differently; `validate` would then report `check-constraint-unexpected` for a legitimate constraint (it refuses, it never guesses), the integration test fails on such a version, and `node scripts/v32-to-v4/spec/v4-checks.mjs --admin env:NAME` regenerates the file.
- **Cutover.** `status` with separately created cutover evidence is covered by unit tests and a database-free CLI test only (valid evidence moves a sealed report to `complete-operator-attested`, which is the operator's statement that the cutover was made and read back and is never verified by this tool; invalid evidence exits 2 as `refused`); nothing here performs or proves a cutover.

## Operator handoff checklist

1. Verify the exact fixture hashes and source fingerprint.
2. Take and independently verify source backups; quiesce writes for the snapshot window.
3. Export an encrypted bundle and verify it before policy review.
4. Review every generated decision; the CLI will not guess duplicate names, enums, timestamps, JSON, or references. The decision owner reads the real values in the output of `review-decisions` (terminal, or a local HTML file that is deleted afterwards), not an agent's summary, and states each choice; the reviewed file records who stated it (`owner`, or `owner-accepted-agent-suggestion`) and any bulk rule verbatim.
5. Prepare a brand-new target, run dry-run, inspect the bound receipt, then apply transactionally.
6. Complete local image copies with `copy-images --passphrase-file` (it fingerprints each object it copies and seals its receipt; point `validate` at the copy with `--image-target-dir` and at the originals with `--image-source-dir`, so the tool re-hashes both ends itself) or provide a signed offline R2 handoff whose receipt carries the SHA-256, size and MIME type observed for every object (attested by the signature, not observed); execute re-embedding externally and provide model/dimension/locator-bound receipts.
7. Run `validate` with `--passphrase-file`: it re-reads the live source and target and compares them with the bundle, the reviewed decisions, the plan and the receipts, and validates any external evidence supplied against the plans it derives itself. A finding refuses. Read the state with `status --passphrase-file`, which will not report a state from a report without a verifying seal.
8. Perform deployment/cutover manually, read back the deployed version, and record separate operator evidence. The CLI can only report `ready-for-cutover` before that evidence, and `complete-operator-attested` after it (the operator's statement, not an observation).
9. Preserve failure artifacts for diagnosis; rollback means pointing the deployment back to untouched v3 configuration, never reverse-copying automatically.
